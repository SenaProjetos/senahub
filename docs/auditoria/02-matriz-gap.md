# Matriz de gap — Refatoração do módulo de Documentos (spec × arquitetura atual)

Cruza `docs/spec-documentos-senahub.md` (36 itens) com `docs/auditoria/01-arquitetura-atual.md`. Toda linha `REUTILIZAR`/`ESTENDER` cita caminho verificado nesta sessão (arquivo aberto, não apenas citado pela auditoria anterior). Onde a auditoria não cobria algo em detalhe suficiente para classificar, foi verificado no código diretamente antes de decidir — ver notas de rodapé de cada linha.

**Régua de esforço** — P = até 1 dia (ajuste/composição de código já existente); M = 2–5 dias (nova coluna/tabela pequena + tela); G = mais de 5 dias / múltiplos PRs (nova entidade central, migração com backfill, ou tela nova de ponta a ponta).
**Régua de risco de regressão** — baixo = não toca caminho em produção hoje; médio = estende contrato/tabela usada em produção; alto = muda comportamento ou schema que outras telas/roles dependem hoje.
**Fase** — conforme item 34 da spec (Fase 1 = tela principal, Fase 2 = documento/revisão/extensões/histórico, Fase 3 = visualizador/tarefas/pins, Fase 4 = comparação avançada + resolução entre revisões). Itens transversais (permissões, auditoria, responsividade, performance, UX, design) foram colocados na Fase 1 porque já se aplicam desde a primeira tela, mas valem para todas as fases seguintes.

## 2. Migrations mínimas

1. **`DocumentoRevisao` (tabela nova)** — `id`, `documentoId` (FK `DocumentoDisciplina`), `numero Int`, `createdAt`, `createdById` — justificativa: nível que falta entre Document e File para agrupar N extensões sob uma revisão (itens 1, 13).
2. **`Upload.revisaoId` (coluna nova, FK)** — liga cada arquivo físico à sua revisão lógica. Backfill: para cada `Upload` existente, criar (ou reaproveitar) uma `DocumentoRevisao` com `numero = Upload.versao` do mesmo `documentoId`; **nenhum registro é descartado** — todo `Upload` sem revisão identificável automaticamente (ex. `documentoId` nulo, caso do gap `auto-store.ts` já registrado em `01-arquitetura-atual.md` §14.5) recebe uma `DocumentoRevisao` avulsa numerada a partir do próprio `Upload.versao`, preservando o arquivo visível e baixável mesmo sem agrupamento perfeito.
3. **`DocumentoDisciplina.titulo/descricao/fase/statusId` (colunas novas, todas opcionais)** — suportam os metadados do Documento lógico da spec (itens 1, 13, 26) sem quebrar linhas existentes (default nulo).
3b. **`NomenclaturaConfig.exigirFase` (coluna nova, `Boolean @default(false)`)** — suporta a exigência de fase configurável por projeto (item 5, atualizado nesta sessão). Extensão da tabela singleton já existente, mesmo padrão do `exigir` atual (nomenclatura). Sem backfill — projetos existentes nascem com `false` (fase opcional, comportamento equivalente ao atual).
4. **`DocumentoStatus` (tabela nova, catálogo)** — espelha `TarefaStatus` (`nome`, `ordem`, `cor`, `ativo`) — suporta item 26 sem reintroduzir enum fixo.
5. **`ListaDocumentos` + `ListaDocumentoItem` (tabelas novas, N:N)** — suporta item 4; sem backfill (conceito não existe hoje, nada a migrar).
6. **`Pendencia.revisaoOrigemId`/`revisaoResolucaoId` (colunas novas, FK a `DocumentoRevisao`)** — suporta item 23. Backfill: pendências existentes recebem `revisaoOrigemId` = a revisão do `uploadId` atual delas (reconstruída via migration 2); `revisaoResolucaoId` fica nulo (ainda não resolvidas entre revisões) — nenhuma pendência é descartada ou perde o `uploadId` original.

Todas as migrations acima são aditivas (colunas/tabelas novas, nada removido nem renomeado) — não quebram leitura/escrita existente de `Upload`/`DocumentoDisciplina`/`Pendencia` enquanto o código antigo não for atualizado para usar os campos novos.

## 3. Compatibilidade retroativa

- **Rotas REST de download/zip** (`GET /api/uploads/[id]/download`, `/zip`, `/disciplina/[id]/zip`, e as três públicas em `/api/p/arquivos/**`) — consumidas por 8+ componentes diferentes (`01-arquitetura-atual.md` §4) e pelo link público enviado por e-mail a clientes. Nenhuma migration proposta acima renomeia ou remove `Upload.caminho`/`nomeArquivo`/`id` — essas rotas continuam funcionando sem alteração de contrato mesmo depois de `Upload` ganhar `revisaoId`.
- **`revisoesDoDocumento()`** (`src/modules/uploads/queries.ts:186-193`) — consumida hoje por `ComparadorRevisoes`. Ao introduzir `DocumentoRevisao`, a função precisa continuar retornando o mesmo formato de saída (lista de `Upload` por `documentoId`) para não quebrar o comparador existente — pode passar a agrupar por `revisaoId` internamente sem mudar o contrato externo.
- **`GET /api/coordenacao/frag/[uploadId]`** e **`GET /api/dwg/[desenhoId]/dxf`** — servem bytes derivados (`.frag`/`.dxf`) chaveados por `uploadId`, fora do escopo desta refatoração (documento de disciplina) mas dependem de `Upload` existir com o mesmo `id` — preservado, pois nenhuma migration acima toca a chave primária de `Upload`.
- **`enfileirarConversao()`/`enfileirarConversaoDwg()`** (pg-boss, `coordenacao/service.ts`, `dwg/service.ts`) — disparados no POST de upload por `uploadId`; não dependem de `documentoId`/`revisaoId`, seguem funcionando sem alteração.
- **Permissões**: qualquer migração do gate hard-coded (`role==="admin"`) para o catálogo `Permissao` (ponto de decisão do item 28) precisa entrar em produção com uma entrada de seed que replique exatamente o comportamento atual (só admin) antes de qualquer liberação para outros papéis — senão usuários que hoje não conseguem excluir/renomear passam a conseguir do dia para a noite.

## 6. Top 10 riscos (maior chance de quebrar produção, com mitigação)

1. **Mudar a chave de `DocumentoDisciplina`** (item 1/13) reprocessa o agrupamento de todo arquivo já existente — mitigação: migração de backfill idempotente, testada contra uma cópia do banco de produção antes de rodar, com plano de rollback (a chave antiga continua válida até a migração ser confirmada).
2. **Corrigir o gate hard-coded de permissão** (`role==="admin"`, item 28) pode abrir ações de exclusão/rename para papéis que hoje não têm acesso, ou fechar para quem hoje tem — mitigação: seed de `Permissao` que replique exatamente o comportamento atual antes de qualquer PR tocar o `if` hard-coded.
3. **Novo nível `DocumentoRevisao`** muda o significado de `Upload.versao` de "identidade da revisão" para "atributo dentro da revisão" — qualquer código que hoje lê `Upload.versao` direto (ex. `entregaveisAtuais()`, `src/modules/uploads/validacao.ts:20-30`) precisa ser revisado antes do deploy, senão a lógica de "maior versão = entregável atual" pode ficar inconsistente com a nova estrutura.
4. **Zip routes sem as mesmas capabilities do download individual** (achado já existente, `01-arquitetura-atual.md` §14.1) — se a refatoração tocar essas rotas para adicionar campos novos, é o momento de corrigir o gap de permissão junto, ou o risco de vazamento entre disciplinas persiste/piora com mais superfície de UI.
